## 1. Purpose and release gate

This plan validates every user-visible or security-relevant change between the
last production release and the v0.6.0 preview candidate. It also covers
regressions in adjacent functionality and the production rolling-upgrade shape:

* VMM is upgraded to v0.6.0;
* KMS and Gateway are upgraded to v0.6.0;
* already-running and newly-created CVMs may use either v0.5.11 or v0.6.0 OS
  images at the same time.

The release is accepted only when:

1. all P0 and P1 cases pass on supported production TEE platforms;
2. no v0.5.11 CVM loses key, certificate, storage, network, Gateway, or KMS
   access after the control-plane upgrade;
3. both event-log v1 and v2 attestations are accepted according to policy;
4. negative security cases fail closed and produce actionable logs;
5. upgrade, rollback, reboot, and repeated-operation cases are idempotent;
6. failures are linked to issues and explicitly waived before publishing.

## 4. Rolling-upgrade compatibility matrix (P0)

Run the rows in order on the same staging cluster. `O` and `N` mean OLD and
NEW. The production target is `N/N/N`, with image `O` and `N` mixed.

| ID | VMM | KMS | Gateway | CVM image | Required result |
|---|---:|---:|---:|---:|---|
| COMP-01 | O | O | O | O | Establish baseline: launch, attest, key/cert, HTTPS, persistent data |
| COMP-02 | N | O | O | O running | VMM upgrade does not stop/change existing CVM; all baseline probes pass |
| COMP-03 | N | N | O | O running | Old guest re-attests and obtains the same app-bound key/cert where specified |
| COMP-04 | N | N | N | O running | Old guest remains reachable through Gateway; DNS/TLS/WireGuard recover |
| COMP-05 | N | N | N | O new | Latest VMM can create a fresh old-image CVM; v1 APIs/event log remain accepted |
| COMP-06 | N | N | N | N new | New image launches with v2 event log and all new policy checks |
| COMP-07 | N | N | N | O+N | Run both concurrently with same app and different apps; no cache/identity crossover |
| COMP-08 | N | N | N | O→N upgrade | Upgrade app image; validate identity/key/storage behavior against documented policy |
| COMP-09 | N | N | N | N→O rollback | Roll back while old image remains permitted; verify explicit denial when policy forbids it |
| COMP-10 | N | N | N | O+N reboot | Reboot host and both CVMs; networking, mount, key, cert and registration recover |

For COMP-01 capture a canary app containing persistent encrypted storage, an
HTTP endpoint, SDK key/certificate calls, runtime event emission, and periodic
Gateway/KMS probes. Keep it running through COMP-10.

Additional mandatory assertions:

* upgrading VMM preserves VM config, VM ID, disks, MAC/IP assignment and
  autostart state;
* old guests do not need the removed `EmitEvent` RPC to boot;
* latest KMS distinguishes event-log v1 from v2 and does not reuse a cached
  verification result across image/app/TEE variants;
* latest Gateway accepts existing registered applications and refreshes stale
  DNS/WireGuard state without request-path stalls;
* authentication rollout is staged: configure clients before enforcing tokens;
* rollback restores binaries/config without downgrading or corrupting guest
  data. Any non-backward-compatible state migration must be documented.

## 7. Build, migration and packaging gates

1. Build all release binaries, containers, SDKs and OS images from a clean
   checkout of the candidate commit.
2. Run repository CI plus Rust unit/integration tests, SDK tests, VMM UI build,
   Gateway/KMS/verifier container builds, SPDX/REUSE and CodeQL.
3. Run `test-suites/full-stack-compose/run-upgrade-e2e.sh` with OLD and NEW
   artifacts and archive its state/logs.
4. Compare two independent image builds; explain every differing byte.
5. Verify version output is 0.6.0 and embeds the correct git revision.
6. Verify artifact manifests, checksums, signatures/SBOMs and container tags.
7. Rehearse config migration from untouched v0.5.11 files. Unknown old fields
   must not silently change security behavior.
8. Rehearse rollback after each control-plane upgrade step before allowing the
   next step.

## 8. Execution order

1. Freeze commit and artifact digests; run clean build/package gates.
2. Run unit/integration/SDK tests and simulator negative cases.
3. Establish COMP-01 baseline and snapshot evidence/backups.
4. Execute COMP-02 through COMP-10 without recreating the baseline canary.
5. Run ATT, AUTH, GST, VMM, STO and GKW suites on TDX.
6. Run PLAT suites on GPU/GCP/AWS/AMD environments.
7. Run REG suite, chaos/restart cases, rollback and cleanup.
8. Produce a signed result table: `Pass`, `Fail`, `Blocked`, or `Waived`, with
   issue/evidence links for every non-pass result.

## 9. Final release checklist

- [ ] Candidate tag points to the audited commit (or this document is refreshed for the new commit).
- [ ] OLD and NEW artifact digests are recorded.
- [ ] All COMP cases pass with old and new images simultaneously online.
- [ ] Event-log v1 compatibility and event-log v2 canonical replay pass.
- [ ] Authentication is enabled on production admin surfaces and rollout order is documented.
- [ ] KMS/Gateway upgrade and rollback rehearsals pass.
- [ ] Platform owners sign off TDX, NVIDIA, GCP, AWS and advertised AMD support.
- [ ] No P0/P1 failure remains unwaived.
- [ ] Known limitations and breaking changes are included in preview release notes.
- [ ] Evidence bundle and issue list are archived.
